Chapter 1: Introduction to Serverless Computing

Serverless computing is a way to build applications without managing long-running servers yourself. The word serverless does not mean there are no servers. It means that the cloud provider operates the servers, patches the operating systems, manages capacity, replaces unhealthy machines, and exposes higher-level services that you compose. A traditional web application often begins with a virtual machine, a web server, a process manager, a deployment script, a firewall, and monitoring. A serverless application begins with events, functions, permissions, and managed data services.

In the traditional model, teams plan instance sizes, install runtime versions, configure load balancers, and decide how many machines should be running at 2 p.m. and at 2 a.m. When traffic grows, the team adds capacity; when traffic falls, unused capacity may still cost money. In a serverless model, you describe what should happen when an event occurs. AWS Lambda runs code when requested. Amazon SQS stores messages until a worker is ready. Amazon SNS broadcasts a notification to many subscribers. DynamoDB stores data without requiring you to administer database servers. CloudWatch records logs and metrics. EventBridge routes business events between systems.

Browser or Service | v Managed AWS Event Source | v Lambda Function | v Managed Data, Queue, Topic, or API

Event-driven computing is the heart of serverless design. Instead of one service directly waiting for another service to finish, one service emits an event such as OrderCreated, PaymentCaptured, or FileUploaded. Other components react independently. This produces systems that are easier to scale, easier to extend, and often more resilient because temporary failures can be retried through queues.

Benefits

Scalability: Lambda can scale by running more concurrent executions, SQS can buffer spikes, and SNS can fan out events. Reduced costs: many services charge based on requests, duration, storage, or messages rather than idle servers. Faster deployment: infrastructure can be described as code. Reduced maintenance: AWS handles many operational tasks.

Common AWS services

Lambda runs code. API Gateway exposes HTTP APIs. SQS queues work. SNS publishes notifications. DynamoDB stores records. CloudWatch observes systems. EventBridge routes events by pattern. These services are building blocks, not a full architecture by themselves.

For beginners, the most important mental shift is to stop thinking about a single program that controls everything. Think in small capabilities. One Lambda validates an HTTP request. Another Lambda consumes a queue. A topic announces a business fact. A database table records durable state. Each component has a clear responsibility and communicates through well-defined events.

Quick quiz

  1. What does serverless really remove from your daily work?
    Show answer

    It removes most server management tasks, not the physical servers themselves.

  2. Why are events important?
    Show answer

    Events let services communicate through facts and triggers instead of tight, synchronous dependencies.

Chapter summary

Key Takeaways

  • Serverless means managed infrastructure and event-driven building blocks.
  • Lambda, SQS, SNS, DynamoDB, API Gateway, CloudWatch, and EventBridge commonly work together.
  • Production systems still need security, monitoring, failure handling, and cost awareness.

Common Mistakes

  • Treating serverless as magic instead of managed infrastructure with quotas, permissions, and operational behavior.
  • Copying examples without understanding names, stages, regions, and IAM resources.

Best Practices

  • Start small, deploy often, observe logs and metrics, and make every asynchronous workflow safe to retry.
  • Document event shapes and keep examples close to the code that produces or consumes them.

Chapter 2: Understanding the Serverless Framework

The Serverless Framework is a developer tool that turns a project directory and a serverless.yml file into deployed cloud infrastructure. It packages your functions, creates or updates AWS CloudFormation stacks, configures event sources, and helps you run common commands. You can think of it as a convenient layer over infrastructure as code and deployment automation.

Without a framework, you would need to manually create Lambda functions, IAM roles, API Gateway routes, SQS event source mappings, SNS subscriptions, log groups, and output values. Manual setup is educational once, but it becomes risky when repeated. A missed permission or a differently named queue can break a deployment. The Serverless Framework keeps the desired state in a file that can be reviewed, versioned, and deployed consistently.

npm install -g serverless

This command uses npm to install the Serverless Framework command line tool globally. Globally means the serverless command is available from your terminal in many directories. In production teams, you may also pin the framework version in project tooling so every developer and continuous integration job uses the same major version.

serverless --version

This command checks that the tool is installed and prints the installed version. Version awareness matters because framework syntax and plugin behavior can change between major releases. In this lesson, examples use a modern frameworkVersion: '4' style and Node.js 22 Lambda runtime examples.

Infrastructure as Code: The point is not merely typing fewer console clicks. The point is repeatability. A pull request can show that you added a queue, changed a timeout, or introduced an IAM permission before it reaches production.

Deployment automation is especially useful for event-driven systems because every connection has two sides. If an SQS queue triggers a Lambda, AWS needs the queue, the function, an event source mapping, and permissions. If an SNS topic invokes a Lambda, AWS needs the topic, subscription, Lambda permission, and often logging and retry configuration. The Serverless Framework can generate the supporting CloudFormation for common cases while still allowing you to define raw CloudFormation resources when you need more control.

  2. Why should teams avoid clicking resources together manually?
    Show answer

Chapter 3: Introduction to serverless.yml

serverless.yml is the central configuration file for a Serverless Framework service. It describes the service name, framework version, provider settings, functions, events, environment variables, IAM permissions, plugins, packaging rules, and CloudFormation resources. Beginners should treat it as both a deployment recipe and a living architecture document.

project/
├── src/
│   ├── handlers/
│   └── services/
├── serverless.yml
├── package.json
└── README.md

The project structure above separates handler files from business services. A handler is the thin Lambda entry point that receives an AWS event. A service module contains reusable business logic such as validating an order, calculating totals, writing to DynamoDB, or publishing to SNS. This separation makes unit testing easier and keeps the deployment configuration understandable.

A small service can have one serverless.yml. A larger system might have several services, each with its own deployment boundary. For example, an order API service may own HTTP routes and the orders table, while an analytics service may subscribe to events and write reports. Boundaries should follow ownership and lifecycle. If two functions must always deploy together and share the same table, they may belong in one service. If they are owned by different teams and change independently, separate services are safer.

Beginner rule: Read serverless.yml from top to bottom and ask: What is this service called? Which AWS account and region will receive it? Which functions will run? Which events trigger them? Which resources will be created? Which permissions are granted?

YAML is whitespace-sensitive. Indentation creates hierarchy. Two spaces are common. Tabs should be avoided. A tiny indentation error can move an event outside a function or place a property under the wrong parent. Use an editor with YAML validation and commit small changes so problems are easier to find.

Chapter 4: Anatomy of serverless.yml

A useful serverless.yml starts with high-level identity, then provider defaults, then functions and resources. The service name becomes part of generated stack names and resource names, so choose something stable and meaningful.

service: order-service
frameworkVersion: '4'

provider:
  name: aws
  runtime: nodejs22.x
  region: us-east-1
  stage: dev
  timeout: 10
  memorySize: 256
  architecture: arm64

service names the deployable unit. frameworkVersion helps prevent accidental deployments with incompatible CLI versions. provider.name selects AWS. runtime chooses the Lambda language environment. region selects where resources are created. stage names the environment, such as dev, staging, or prod. timeout defines maximum function runtime in seconds unless overridden per function. memorySize controls available memory and proportionally influences CPU. architecture can be arm64 or x86_64; arm64 is often cost-effective, but native dependencies must support it.

Provider defaults reduce repetition, but production services often override settings for specific functions. A public HTTP function may need a short timeout so clients are not left waiting. A batch worker may need more memory or a longer timeout. A scheduled cleanup job may have different environment variables. The default is a starting point, not a prison.

functions:
  createOrder:
    handler: src/orders/create.handler
    timeout: 6
    memorySize: 512
  processOrder:
    handler: src/orders/process.handler
    timeout: 60
    memorySize: 1024
Production warning: A high global timeout can hide slow code and cause expensive retries. Set timeouts intentionally. For SQS-triggered Lambdas, coordinate Lambda timeout and queue visibility timeout so the message does not reappear while still being processed.

Chapter 5: Functions Deep Dive

An AWS Lambda function is a small unit of compute that runs in response to an event. The event may be an HTTP request, a queue message, an SNS notification, a schedule, an S3 object creation, or a custom EventBridge event. Lambda creates execution environments as needed, invokes your handler, captures logs, and returns a response to the event source when appropriate.

Lambda functions are stateless from the architecture perspective. You should not rely on local memory or local disk to contain durable business state. AWS may reuse an execution environment for performance, so cached clients can help, but the function must still work if started cold with no previous memory. Durable state belongs in a database, queue, object store, or another managed service.

functions:
  hello:
    handler: src/handlers/hello.handler

The function key hello is the logical name inside the service. The handler path src/handlers/hello.handler means the file is src/handlers/hello.js in a JavaScript project and the exported function is named handler. The Serverless Framework packages the code and tells Lambda which module export to call.

export const handler = async () => {
  return {
    statusCode: 200,
    body: JSON.stringify({
      message: 'Hello World'
    })
  };
};

export makes the function available to Lambda's module loader. async lets the handler use await for promises such as database writes or SDK calls. The return value shown is an HTTP-style response: status code plus a JSON string body. For non-HTTP events, the return value may be ignored or interpreted differently. For SQS, success means the batch can be deleted; throwing an error means messages may be retried.

functions:
  createOrder:
    handler: src/orders/create.handler

  getOrder:
    handler: src/orders/get.handler

  deleteOrder:
    handler: src/orders/delete.handler

Multiple functions should be organized around responsibilities. A create-order HTTP function validates input and starts the workflow. A get-order function reads the database. A delete-order function may mark an order canceled rather than physically delete it. A process-order worker consumes queue messages and performs slow work. Separating these concerns improves security because each function can receive only the permissions it needs.

The Lambda execution lifecycle has several phases. During initialization, the runtime loads your module and creates top-level objects. During invocation, Lambda passes an event and context object to your handler. After the handler resolves or rejects, Lambda freezes or reuses the environment. Cold starts happen when AWS must create a new environment. You can reduce cold-start impact by keeping packages small, avoiding heavy initialization, and choosing appropriate memory.

import { SNSClient, PublishCommand } from '@aws-sdk/client-sns';
const sns = new SNSClient({}); // safe to reuse across invocations

export const handler = async (event) => {
  const order = JSON.parse(event.body || '{}');
  await sns.send(new PublishCommand({
    TopicArn: process.env.ORDER_TOPIC_ARN,
    Message: JSON.stringify({ type: 'OrderCreated', order })
  }));
  return { statusCode: 202, body: JSON.stringify({ accepted: true }) };
};

Chapter 6: Events and Event-Driven Architecture

Events are signals that something happened. In the Serverless Framework, the events section under a function tells AWS what should trigger that function. A single function can have multiple events, but production designs usually keep triggers focused. Event-driven architecture replaces direct orchestration with event publication and reaction.

Command: Create Order | v Order API Lambda records intent | v Event: OrderCreated | +--> Payment workflow +--> Email notification +--> Analytics update
functions:
  listOrders:
    handler: src/orders/list.handler
    events:
      - httpApi:
          path: /orders
          method: get

An HTTP API event creates an API Gateway route. When a browser or client sends GET /orders, API Gateway invokes the Lambda. HTTP functions should validate input, authenticate callers, and return clear status codes. They should not perform long background work while the client waits if that work can be queued.

functions:
  cleanupExpiredOrders:
    handler: src/orders/cleanup.handler
    events:
      - schedule: rate(5 minutes)

Scheduled events run on a timer. They are useful for cleanup, reconciliation, polling a third-party API, or publishing reminders. Production scheduled jobs should be idempotent because retries or overlapping work can occur.

functions:
  processUpload:
    handler: src/uploads/process.handler
    events:
      - s3:
          bucket: uploads
          event: s3:ObjectCreated:*

S3 events invoke code when objects change. They are common for image processing, data imports, and document workflows. Avoid writing processed files back to the same prefix without filters, or you can accidentally trigger recursive processing.

functions:
  handleOrderEvent:
    handler: src/events/order.handler
    events:
      - eventBridge:
          pattern:
            source:
              - app.orders

EventBridge is a routing layer for events. A pattern can match source, detail type, account, region, or fields inside the detail object. It is excellent for domain events that may cross service boundaries. SNS is often used for high-throughput fan-out and direct subscriber delivery; EventBridge is often used for event bus routing, SaaS integration, and rule-based filtering.

Quick quiz

  1. When should you queue work instead of doing it in an HTTP request?
    Show answer

    When the work is slow, retryable, or not needed before responding to the client.

  2. What is a risk with S3 triggers?
    Show answer

    Recursive triggers if outputs are written where they match the same event rule.

Chapter summary

Key Takeaways

  • Events connect AWS services to Lambda functions.
  • HTTP, schedule, S3, and EventBridge triggers serve different use cases.
  • Design events as business facts and consumers as independent reactions.

Common Mistakes

  • Treating serverless as magic instead of managed infrastructure with quotas, permissions, and operational behavior.
  • Copying examples without understanding names, stages, regions, and IAM resources.

Chapter 7: Amazon SQS Deep Dive

Amazon Simple Queue Service, or SQS, is a managed message queue. A queue stores messages from producers until consumers are ready to process them. This simple idea solves many production problems. If order creation receives a sudden traffic spike, the API Lambda can place messages in SQS quickly and return to customers. Worker Lambdas can process messages at a controlled pace. If a downstream database is briefly slow, messages remain in the queue instead of being lost.

Producer | sends message v SQS Queue | polled by Lambda event source mapping v Consumer Lambda | writes result v Database or external service

SQS decouples services in time. The producer does not need the consumer to be online at the exact same moment. It also decouples scaling. The producer may handle short bursts while the consumer scales based on backlog. This is a core production pattern for serverless systems because Lambda can scale quickly, but every downstream system still has limits. Queues provide backpressure.

Queue types

Standard queues provide very high throughput, at-least-once delivery, and best-effort ordering. At-least-once means a message can occasionally be delivered more than once, so consumers must be idempotent. Best-effort ordering means messages usually arrive in order, but strict ordering is not guaranteed. FIFO queues provide strict ordering within a message group and deduplication support. FIFO is useful when sequence matters, such as ledger updates, but it has different throughput characteristics and requires .fifo queue names.

FeatureStandardFIFO
OrderingBest effortGuaranteed within message group
ThroughputVery highLower or partitioned by groups
DuplicationPossibleControlled with deduplication
Use caseMost background jobsOrdered workflows and ledgers
resources:
  Resources:
    OrdersQueue:
      Type: AWS::SQS::Queue
      Properties:
        QueueName: orders-queue

The resources section passes raw CloudFormation into the deployment. OrdersQueue is the logical ID inside the CloudFormation template. Type: AWS::SQS::Queue tells AWS which resource to create. QueueName sets the physical name. In real systems, include the stage in names so dev and prod do not collide.

functions:
  processOrders:
    handler: src/orders/process.handler
    events:
      - sqs:
          arn:
            Fn::GetAtt:
              - OrdersQueue
              - Arn
          batchSize: 10

When Lambda is triggered by SQS, AWS creates an event source mapping. That mapping polls the queue, receives messages, invokes the Lambda with a batch, and deletes successfully processed messages. Your function does not usually call DeleteMessage directly when using the managed event source mapping; Lambda handles deletion after successful processing. If your handler throws, messages stay in the queue and become visible again after the visibility timeout.

Batch processing controls how many messages are delivered in one invocation. A batch size of 10 can reduce cost because one invocation handles ten messages, but it also means an error can affect the whole batch unless partial batch response is configured. Production workers should consider partial failures, idempotency keys, and per-record error handling.

export const handler = async (event) => {
  for (const record of event.Records) {
    const message = JSON.parse(record.body);
    await processOrder(message);
  }
};

async function processOrder(message) {
  console.log('Processing order', message.orderId);
  // Validate, write durable status, call downstream services safely.
}

Visibility timeout

Visibility timeout is the period during which a received message is hidden from other consumers. Imagine a worker receives an order message and needs 20 seconds to process it. If the visibility timeout is 30 seconds, no other worker sees it during normal processing. If the worker crashes, the timeout expires and another worker can retry. If the visibility timeout is too short, two workers may process the same message concurrently. If it is too long, failed messages take too long to retry.

T0: message received and hidden T0-T30: worker processes message Success before T30: Lambda deletes message Failure or timeout: message becomes visible again after T30

Dead letter queues

A dead letter queue, or DLQ, stores messages that repeatedly fail. Without a DLQ, a poison message can be retried forever and consume capacity. With a DLQ, operations teams can inspect failed payloads, fix bugs, replay messages, or contact affected customers. A redrive policy connects the main queue to the DLQ and sets a maximum receive count.

resources:
  Resources:
    OrdersDeadLetterQueue:
      Type: AWS::SQS::Queue
      Properties:
        QueueName: orders-dlq-${self:provider.stage}
    OrdersQueue:
      Type: AWS::SQS::Queue
      Properties:
        QueueName: orders-queue-${self:provider.stage}
        VisibilityTimeout: 90
        RedrivePolicy:
          deadLetterTargetArn:
            Fn::GetAtt:
              - OrdersDeadLetterQueue
              - Arn
          maxReceiveCount: 5

deadLetterTargetArn points to the DLQ. maxReceiveCount: 5 means SQS moves the message to the DLQ after it has been received and failed enough times. Choose this number based on how transient your failures are. A temporary database timeout may deserve several retries. A malformed message will never succeed until code or data changes.

Real-world order processing system

Customer | POST /orders API Gateway | invokes CreateOrder Lambda | SendMessage SQS Orders Queue | batch poll Worker Lambda | PutItem / UpdateItem DynamoDB Orders Table

In this lifecycle, the customer submits an order and receives a fast 202 Accepted response. The API Lambda validates the request, creates an order ID, stores an initial record or sends a message, and returns. The queue absorbs traffic. The worker Lambda processes payment checks, inventory reservations, or fulfillment tasks. The database records status transitions such as PENDING, PROCESSING, COMPLETED, or FAILED. If the worker fails, SQS retries. If the message keeps failing, the DLQ preserves it for investigation.

Production SQS consumers should be idempotent. If the same message is delivered twice, processing it twice should not charge the customer twice or ship two packages. Use a business key such as orderId, conditional writes in DynamoDB, or a processed-events table. Log message IDs and correlation IDs. Alarm on visible message age, DLQ depth, and Lambda errors. These practices turn a simple queue into a reliable operational workflow.

Chapter 8: Amazon SNS Deep Dive

Amazon Simple Notification Service, or SNS, is a managed publish/subscribe service. A publisher sends one message to a topic. SNS then delivers that message to every subscribed endpoint. This is called fan-out. SNS is perfect when one business event should cause several independent reactions. For example, OrderCreated may need to email a customer, notify inventory, update analytics, and start fraud checks. The order service should not need to know how every downstream team works.

Publisher | Publish v SNS Topic / | \ v v v Email Lambda SQS

A topic is a named communication channel. Publishers do not send directly to subscribers; they publish to the topic ARN. Subscribers can be Lambda functions, email addresses, SMS numbers, HTTP endpoints, mobile push endpoints, or SQS queues. SNS handles delivery attempts according to endpoint type and configuration.

resources:
  Resources:
    UserEventsTopic:
      Type: AWS::SNS::Topic
      Properties:
        TopicName: user-events

The CloudFormation resource above creates a topic. The logical ID is UserEventsTopic. The resource type is AWS::SNS::Topic. TopicName controls the topic name. In production, include the stage or service name to avoid collisions and to make dashboards clear.

functions:
  processUserEvent:
    handler: src/users/process.handler
    events:
      - sns:
          arn:
            Ref: UserEventsTopic

A Lambda SNS subscription invokes a function whenever the topic receives a message. Ref: UserEventsTopic resolves to the topic ARN in this context. The function receives an event containing Records, each with SNS metadata and the message body. Consumers should parse the message, validate the event type and version, then perform their work.

export const handler = async (event) => {
  for (const record of event.Records) {
    const envelope = record.Sns;
    const message = JSON.parse(envelope.Message);
    console.log('SNS message', envelope.MessageId, message.type);
    if (message.type === 'UserRegistered') {
      await sendWelcomeEmail(message.detail);
    }
  }
};

SNS subscribers

Lambda subscribers are good for immediate compute reactions. Email subscribers are useful for human notifications but require confirmation and are not a replacement for transactional email systems at scale. SMS subscribers send text messages, but cost, compliance, and regional rules matter. HTTP endpoints let external systems receive messages after confirming subscription. SQS queues are the most important production subscriber type because they combine fan-out with buffering and independent retries.

resources:
  Resources:
    OrderEventsTopic:
      Type: AWS::SNS::Topic
      Properties:
        TopicName: order-events-${self:provider.stage}
    EmailQueue:
      Type: AWS::SQS::Queue
      Properties:
        QueueName: email-events-${self:provider.stage}
    AnalyticsQueue:
      Type: AWS::SQS::Queue
      Properties:
        QueueName: analytics-events-${self:provider.stage}
    EmailSubscription:
      Type: AWS::SNS::Subscription
      Properties:
        TopicArn:
          Ref: OrderEventsTopic
        Protocol: sqs
        Endpoint:
          Fn::GetAtt: [EmailQueue, Arn]
    AnalyticsSubscription:
      Type: AWS::SNS::Subscription
      Properties:
        TopicArn:
          Ref: OrderEventsTopic
        Protocol: sqs
        Endpoint:
          Fn::GetAtt: [AnalyticsQueue, Arn]

Fan-out pattern

Order Created | v SNS Topic / | \ / | \ v v v Email Analytics Inventory Queue Queue Queue

Enterprises use fan-out because it protects the publishing service from downstream complexity. The order service publishes one event and moves on. The email team owns email processing. The analytics team owns analytics processing. The inventory team owns stock reservation. Each subscriber can scale, retry, deploy, and fail independently. Adding a new subscriber should not require changing the publisher if the event contract already contains the needed information.

SNS + SQS pattern

The SNS plus SQS pattern is one of the most reliable event-driven designs on AWS. SNS provides broadcasting. SQS provides buffering, retry control, DLQs, and independent consumer pace. If SNS directly invokes three Lambda functions and one function has a bug, that function's retry behavior is separate but there is no queue backlog to inspect in the same way. With SQS subscriptions, each consumer has its own queue and DLQ. A broken analytics worker does not block email delivery or inventory processing.

functions:
  publishOrder:
    handler: src/orders/create.handler
    environment:
      ORDER_TOPIC_ARN:
        Ref: OrderEventsTopic

  sendEmail:
    handler: src/email/worker.handler
    events:
      - sqs:
          arn:
            Fn::GetAtt: [EmailQueue, Arn]
          batchSize: 5

  updateAnalytics:
    handler: src/analytics/worker.handler
    events:
      - sqs:
          arn:
            Fn::GetAtt: [AnalyticsQueue, Arn]
          batchSize: 10

Message filtering can reduce unnecessary delivery. A subscriber can request only events with attributes such as eventType = OrderCreated. Filtering saves cost and simplifies consumers, but do not rely on it as your only validation. Consumers should still check message type and version because event contracts evolve.

E-commerce notification walkthrough

When an order is placed, the order API Lambda writes an order record and publishes OrderCreated to SNS. SNS receives the event and fans it out to an email queue, analytics queue, and inventory queue. The email worker sends a confirmation. The analytics worker updates metrics. The inventory worker reserves stock. If the email provider is temporarily down, only the email queue builds backlog. Inventory and analytics continue. If the inventory message repeatedly fails because a SKU is invalid, that message moves to the inventory DLQ for investigation. The order event remains a durable business fact that multiple teams can use.

Chapter 9: Resources Section

The resources section lets you define AWS CloudFormation resources that are not fully described by simple function events. This is where you create DynamoDB tables, SQS queues, SNS topics, alarms, IAM policies, and other infrastructure. Serverless Framework merges this CloudFormation into the generated template.

resources:
  Resources:
    OrdersTable:
      Type: AWS::DynamoDB::Table
      Properties:
        TableName: orders-${self:provider.stage}
        BillingMode: PAY_PER_REQUEST
        AttributeDefinitions:
          - AttributeName: orderId
            AttributeType: S
        KeySchema:
          - AttributeName: orderId
            KeyType: HASH

CloudFormation tracks resource creation, updates, and deletion as a stack. If you change the table name, AWS may need replacement. If you add a queue redrive policy, AWS updates the existing queue. Infrastructure as code means these changes are visible in source control. Production teams should understand which changes are destructive before deploying.

Chapter 10: Environment Variables

Best practice is to keep configuration explicit. If a function needs a topic ARN, put it in that function's environment or provider environment and grant matching IAM permissions. Avoid scattering literal names through code.

Chapter 11: IAM Permissions

IAM controls what your functions can do. A Lambda execution role should have the smallest set of permissions needed. Beginners often start with Resource: '*', but production services should scope actions to specific queues, topics, tables, or log groups whenever possible.

provider:
  iam:
    role:
      statements:
        - Effect: Allow
          Action:
            - sqs:SendMessage
          Resource:
            Fn::GetAtt: [OrdersQueue, Arn]
        - Effect: Allow
          Action:
            - sns:Publish
          Resource:
            Ref: OrderEventsTopic
        - Effect: Allow
          Action:
            - dynamodb:PutItem
            - dynamodb:GetItem
          Resource:
            Fn::GetAtt: [OrdersTable, Arn]

Effect is usually Allow or Deny. Action names API operations. Resource scopes where the action applies. Least privilege reduces blast radius if a function is compromised or buggy.

import { SNSClient, PublishCommand } from '@aws-sdk/client-sns';
import crypto from 'node:crypto';
const dynamodb = new DynamoDBClient({});
const sns = new SNSClient({});
export const handler = async (event) => {
  const body = JSON.parse(event.body || '{}');
  const orderId = crypto.randomUUID();
  await dynamodb.send(new PutItemCommand({
    TableName: process.env.ORDERS_TABLE,
    Item: { orderId: { S: orderId }, status: { S: 'PENDING' } }
  }));
  await sns.send(new PublishCommand({
    TopicArn: process.env.ORDER_TOPIC_ARN,
    Message: JSON.stringify({ type: 'OrderCreated', version: 1, detail: { orderId, items: body.items || [] } }),
    MessageAttributes: { eventType: { DataType: 'String', StringValue: 'OrderCreated' } }
  }));
  return { statusCode: 202, body: JSON.stringify({ orderId, status: 'PENDING' }) };
};

Chapter 16: Troubleshooting

Common serverless failures are usually configuration mismatches. An invalid ARN means a reference points to the wrong resource or region. Missing permissions mean IAM allowed too little. Lambda timeout means the function exceeded its configured duration. A queue not receiving messages may indicate the producer is publishing to the wrong URL, the subscription policy is missing, or the event filter excludes the message. SNS delivery failures may come from unconfirmed subscriptions, endpoint errors, or missing SQS queue policy. Deployment failures often come from YAML indentation, duplicate names, or CloudFormation replacement constraints.

IssueLikely causeFix
Invalid ARNWrong stage, region, or referenceUse Ref or Fn::GetAtt and check outputs
Access deniedIAM missing action or resourceAdd least-privilege statement
TimeoutSlow downstream or too small timeoutOptimize, queue work, or adjust timeout
DLQ growingPoison message or code bugInspect payloads, fix consumer, redrive safely

Chapter 17: Best Practices

For functions, use single responsibility, small handlers, shared libraries, explicit input validation, and structured errors. For SQS, configure DLQs, visibility timeouts, batch sizes, idempotency, and alarms. For SNS, use fan-out design, message attributes, filtering, event versioning, and clear contracts. For security, apply least privilege, encrypt sensitive data, use a secrets manager for secrets, and review public endpoints. For cost optimization, tune memory, avoid unnecessary invocations, batch queue work, and monitor idle or failing resources.

Production mindset: Every event may be duplicated, delayed, retried, or processed after a deployment. Design for those realities from the beginning.

Appendix: Production Readiness Checklist

This appendix gives you a final review checklist before using the lesson patterns in a real workload. Treat every Lambda handler as a small production service. It needs ownership, logging, metrics, alarms, permissions, deployment history, and rollback strategy. Treat every event as a public contract between systems. Once consumers depend on an event shape, changing field names or meanings can break downstream workflows even if the publisher still deploys successfully. Version event schemas, add optional fields before removing old ones, and communicate changes.

For Lambda functions, confirm that package size is reasonable, dependencies are actively maintained, timeouts match the trigger, and memory is tested with realistic payloads. Keep SDK clients outside handlers when possible, but do not store customer state in global variables. Validate every external input, including messages from queues and topics, because a compromised or buggy publisher can send malformed data. Prefer explicit error classes and structured logs so operators can distinguish validation failures from dependency failures.

For SQS queues, configure a dead letter queue, alarm on visible message age, alarm on DLQ message count, and document the redrive process. Check that the visibility timeout is longer than the Lambda timeout plus expected retry overhead. Choose batch size based on work cost and failure isolation. If one bad record should not fail nine good records, implement partial batch responses or handle each record with durable per-record status. Make consumers idempotent by using order IDs, event IDs, conditional writes, or deduplication records.

For SNS topics, document who publishes, who subscribes, what message attributes exist, and what delivery guarantees each subscriber expects. When using SNS to SQS subscriptions, remember that queues often need policies allowing the topic to send messages. Use filter policies to reduce noise, but keep consumer-side validation. Include correlation IDs so a single order can be followed through the API function, topic publish, queue delivery, worker processing, and database update.

For security, avoid wildcard permissions in production examples unless there is a documented reason. Scope IAM resources to CloudFormation references. Encrypt data at rest where appropriate. Store sensitive values in a secrets service rather than plain text environment variables. Review API authentication and authorization separately from Lambda code. For cost, watch high retry loops, oversized memory, unnecessary scheduled frequency, and queues that silently accumulate messages. Cost optimization is not just making things cheaper; it is removing waste while preserving reliability.

Finally, practice failure. Send a malformed message and confirm it reaches a DLQ. Temporarily deny a permission in a development stage and read the error. Increase worker latency and observe queue age. Deploy a new subscriber without changing the publisher. These exercises build intuition and make production incidents less surprising.
